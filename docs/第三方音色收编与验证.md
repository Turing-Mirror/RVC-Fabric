# 第三方音色收编与验证

第三方音色指的是从公开社区站点（目前只有 Hugging Face）索引来的 RVC 模型。
**我们不转存这些文件**，清单里存的是直链，用户点下载时客户端直接去源站拉。
CNB 上只多出一条几百字节的清单条目和一张封面图。

商店里第三方音色和图灵镜自有音色长得一模一样——名字、封面、系列、作者、
下载安装流程都一致。这是刻意的：用户不需要知道东西从哪来。也正因为如此，
**没有验证过的条目不允许发布**。

---

## 一条音色要走的三步

```
1. 收编   scripts/add_thirdparty_voice.py   → 生成 YAML（查 API，不下载）
2. 验证   scripts/verify_voice_pack.py      → 下载、拆开、确认，把结果写回 YAML
3. 发布   scripts/build_catalog.py build    → 编译进 index.json，push 到 CNB
```

第 2 步不做，第 3 步会直接报错并拒绝编译这条音色。

---

## 1. 收编

```bash
python scripts/add_thirdparty_voice.py --hf AppleAndA/ATRI_RVC_Models \
    --name ATRI --tag 二次元 --series ATRI
```

脚本查 Hugging Face 的 tree API 拿文件列表、体积和 LFS oid，**一个字节的模型
都不下载**，然后判断形态：

| 形态 | 判断依据 | 清单字段 |
|---|---|---|
| `voice_files` | 仓库里有 >50KB 的 `.pth` | `pth_url` + `index_url` |
| `voice_pack` | 只有 zip | `pack_url` |

`voice_files` 是更干净的形态：清单直接点名要哪两个文件，仓库里的训练中间产物
（`G_*.pth` / `D_*.pth`，动辄好几百 MB）根本不会被下载。

自动填的：`author` / `author_url` / `source_url` / `sha256` / `size_bytes`。
要人工的：`name` / `tag` / `series` / `description`。

`date` 写的是**收录日期**，不是上游的上传日期。

### 封面

脚本拿角色名去 Bangumi 搜，下载到发布仓的 `ch-banner/<id>.jpg`，YAML 里写
`cover: ch-banner/<id>.jpg`（相对路径，客户端拼成 CNB 的 raw URL）。
封面图**由我们托管**，不热链 HF 或 Bangumi——热链会挂。

真人音色（`--real-person`）不配封面。

## 2. 验证

```bash
python scripts/verify_voice_pack.py --hf AppleAndA/ATRI_RVC_Models \
    --pth ATRI_e500_s206500.pth \
    --index added_IVF4334_Flat_nprobe_1_ATRI_v2.index
```

大合集仓必须用 `--pack` 指定包内路径：

```bash
python scripts/verify_voice_pack.py --hf ArkanDash/rvc-genshin-impact \
    --pack "prezipped/v2/furina-jp 275 epochs 48k v2.zip"
```

### 它查什么

| 检查 | 挡掉什么 |
|---|---|
| `zip_ok` | 压缩包损坏、包内路径会写到解压目录外 |
| `files_ok` | 直链形态下 `.pth` 体积不足 |
| **`pth_struct_ok`** | **能解压、有 .pth，但那不是 RVC 模型** |
| `index_readable` / `index_present` | index 损坏或过小 |

`pth_struct_ok` 是分水岭。前几条挡不住最典型的坑：Hugging Face 上大量同名
模型其实是 SoVITS / VITS，压缩包一样能解开、里面一样有 `.pth`、体积也够，
装完点「开启变声」才崩。这一条用 torch 打开检查点，确认有 RVC 必需的
`weight` / `config` 键。

**没有 `pth_struct_ok` 的条目，`build_catalog` 会拒绝编译。**

### 安全前提

`.pth` 是 pickle，反序列化等于执行任意代码。客户端为此硬性要求 sha256
（`store.rs`：缺哈希直接拒装）。验证脚本同理——**只用
`torch.load(weights_only=True)`**。安全模式下加载不了的包，结论是「验证不
通过」，不是「换个不安全的方式再试一遍」。

### 哈希的含义变了

收编时写进 YAML 的 `sha256` 来自 Hugging Face 的 API 元数据（`lfs.oid`），
含义是「HF 说它是这个」。跑完验证之后，那个值是我们**自己下载、自己算、
自己打开过**的，含义是「我们确认过」。

这也是为什么锚点是哈希而不是文件名：上游把 zip 换掉 → 哈希对不上 →
客户端直接拒装 → 我们就知道了。`verified.pth` / `verified.index` 记的文件名
只是证据和排障线索，**客户端不读它**，仍然用自己那套启发式挑文件。让客户端
去依赖清单里的文件名，只会多一种失败模式，而哈希已经覆盖了同一件事。

### 体积

`size_bytes` 记的是**用户实际要下载的总量**。`voice_files` 形态下是
pth + index 之和——ATRI 的 index 有 534 MB，只记 pth 的话商店会显示 57 MB
而实际下 590 MB。

## 3. 发布

```bash
python scripts/build_catalog.py check --strict
python scripts/build_catalog.py build --diff
cd <发布仓> && git add -A && git commit && git push origin main
```

发布仓默认解析顺序：环境变量 `RVCF_CNB_DIR` → 与产品仓同级的
`RVC-Fabric-Release` → 仓内旧位置 `CNB-GIT-RELEASE`。

---

## 环境

验证脚本只依赖标准库，**torch 是可选的**：

- 没有 torch：只做前两层，结论标 `pth_struct_unchecked`。这种条目不应该发布。
- 有 torch：完整验证。CPU 版就够，不需要 CUDA。
- 有 faiss（可选）：index 检查从 `index_present` 升级为 `index_readable`。

准备一个只装 CPU torch 的环境：

```bash
python -m venv .venv-verify
.venv-verify/bin/pip install torch --index-url https://download.pytorch.org/whl/cpu
```

下载缓存默认在产品仓的 `.verify-cache/`（已 gitignore），
可用 `RVCF_VERIFY_CACHE` 改。验过之后可以整个删掉。

## 规矩

1. `id` 一律 `tp-` 前缀，且不得与官方 `voices/` 撞名——`build_catalog` 会挡。
2. 不得写 `fabric_official: true` 或 `publisher: rvc_fabric`——同样会挡。
3. 一条音色一个 YAML。大合集仓不要一条 YAML 塞整个仓库，客户端是按
   「一音色一条」设计的。
4. `series` 即使是第三方也要填。商店的「系列专区」会把官方和第三方合并按
   系列聚合，填了才进得去。
5. 二次元封面用 Bangumi 并人工过目；真人留空。
6. 收录前确认来源仓库的授权说明。授权与版权归上传者和原站，与图灵镜无关，
   商店里对第三方音色有单独的免责确认。
